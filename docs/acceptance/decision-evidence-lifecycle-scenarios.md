# Decision evidence lifecycle E2E scenarios

Run these against a migrated disposable PostgreSQL cluster and a disposable archive directory. Preserve a before snapshot of typed rows and expanded reads. Use the same deterministic busy-day input stream for the before and after replay. Record the code SHA, Alembic revision, commands, counts, bytes, and archive receipts.

1. **Unchanged evaluation:** Evaluate the same instrument twice with the same immutable source versions, values, forecast, portfolio state, rank, risk, and plan terms at different check times. Expect one decision, one plan, one set of payload references, no new paper order, and a daily checkpoint with count two and separate first/last check times. The decision `as_of` stays at its original cutoff. Retry the second evaluation concurrently and expect the same result.
2. **Semantic change:** Change exactly one source revision, freshness state, risk result, expiry, rank, or plan term. Expect a new decision even if both actions are HOLD. Keep legacy input hashes and IDs unchanged. A source timestamp change counts; an evaluation-only generated ID does not.
3. **One fact, one owner:** Publish a decision with expressions, selected expression, portfolio impact, forecast, and plan. Check that every normalized component has one immutable payload or typed source owner, one reference from each consumer, and no inline duplicate. Read it through the ticker API, attribution, Learning, Research, replay, and paper staging. Compare JSON values and numeric precision with the before snapshot. Keep unequal legacy values separate.
4. **Publication reuse:** Repeat the unchanged evaluation and confirm no new decision-backed bundle or payload bytes. A changed decision creates one new publication order and renders the same display object as the canonical decision and plan repositories.
5. **Completed history:** Make a decision and option scan older than 30 days, with one shared dependency. Keep local compact results, scores, reasons, model versions, plan, outcome links, and identities. Archive complete typed rows and dependency versions once. Verify checksum, dependency coverage, and typed scratch restore before compaction. A pending outcome keeps its exact plan, forecast, benchmark, and required prices but does not pin the whole scan.
6. **Protection and failure:** Current decisions/publications, open orders, active investigations, and unfinished calculations remain local. NAS outage, corrupt pack, missing dependency, interrupted checkpoint, conflicting scratch row, or concurrent new reference prevents compaction and leaves source evidence intact. A full-evidence read reports archived or unavailable explicitly.
7. **Cold restore:** Delete only eligible full evidence from the disposable source database. With NAS disconnected, current decisions, paper trading, Learning, and compact history still work. Reconnect NAS, restore a selected decision or scan plus dependencies into scratch PostgreSQL, and compare exact typed values and IDs with the before snapshot.
8. **Accounting:** Capture three daily production samples on the actual PostgreSQL volume. Report physical size, logical growth, archive throughput, backlog, protected bytes, observed filesystem reclamation, and forecast confidence. A forecast below 15 GiB free marks storage degraded and defers optional historical collection without changing the 30-day window or stopping core records. Reusable database pages do not count as filesystem space.
9. **Release:** Verify orders, fills, positions, cash, outcomes, P&L, and attribution links retain their IDs and values. Run the relevant E2E tests, `make guards`, `make check`, and `make release-gate` on one frozen candidate. Complete independent review, managed-runtime smoke, and UI checks for Today, ticker evidence, Research, Learning, and Paper Trading.
